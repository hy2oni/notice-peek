# 저장 구조 분리 — 3단계

`develop` 소스의 SQLite 스키마를 버전 1에서 2로 변경했다.

- `board_catalog`: 앱에 포함된 게시판 카탈로그, 지원 상태와 원본 메타데이터.
- `subscriptions`: 사용자가 선택한 출처와 출처별 최초 수집 여부·수집 결과.
- `notices`: 기존 공지 기록과 읽음·즐겨찾기. 이전 테이블을 그대로 유지한다.

앱 시작 시 번들 JSON으로 카탈로그를 갱신하고, 카탈로그에서 빠진 기존 항목은 임의로 삭제하지 않는다. 출처 목록과 실제 수집 대상은 구독 테이블에서 읽는다. 카탈로그의 수집 확인 상태는 등록 가능한 후보를 뜻한다. 실제 등록 전 재검사와 선택 화면은 4단계에서 연결한다.

## 기존 DB

버전 1 DB는 SQLite backup API로 같은 폴더에 `notices.sqlite3.v1-backup-<임의 식별자>` 백업을 만든 뒤 트랜잭션 안에서 이관한다. `sources`를 `subscriptions`로 옮기고 기존 두 출처를 유지한다. 공지의 모든 필드와 출처별 수집 상태를 보존한다. 수집을 한 번도 하지 않은 구버전 DB도 기존의 두 출처를 구독한 것으로 처리한다.

알 수 없는 출처·잘못된 스키마가 있으면 이관을 취소하고 버전 1 구조를 유지한다. 이관 완료 DB를 다시 열 때는 추가 백업이나 초기화를 하지 않는다. 버전 2 DB는 구버전 앱에서 열 수 없으므로 새 버전을 실제 배포하기 전까지 개인 DB로 개발 실행하지 않는다.

## 신규 DB와 구독 변경

새 DB에는 카탈로그만 넣고 구독은 0개로 시작한다. 구독이 없으면 수집기는 네트워크 요청을 하지 않는다. 아직 최초 선택 화면은 구현되지 않았으므로 이 단계의 소스만 새 DB로 실행하면 공지를 자동 등록하지 않는다.

새 구독의 최초 수집은 일반 글 최근 20건과 고정 글이며 모두 읽음이다. 저장한 과거 공지는 20건으로 자르지 않는다. 후속 수집은 새 ID만 저장하며 기존 제목이나 플래그를 덮어쓰지 않는다.

출처 제거 API는 해당 출처의 공지·읽음·즐겨찾기·수집 상태를 한 트랜잭션으로 삭제하고 카탈로그는 유지한다. 사용자 확인창은 4단계의 화면에서 처리한다. 재구독은 새로운 최초 수집으로 시작한다. 구독마다 식별 토큰을 두어 제거 후 이전 수집 결과가 돌아오거나 같은 출처를 재구독해도 이전 작업이 기록·오류 상태를 되살리지 못하게 했다.

## 검증

- 기존 테스트의 최초 수집 기대값을 20건으로 수정했다.
- 이관 시 기록·플래그·수집 상태·백업 보존, 실패 시 스키마 롤백, 빈 구버전 DB, 무구독 실행, 구독 제거와 재등록, 수집 중 제거·재등록, 추가 학과만 선택하여 수집하는 경우를 검증했다.
- 실제 개인 DB는 읽기 전용으로 열어 작업 폴더에 복제했다. 복제본 이관 후 공지 70건의 모든 필드와 출처 상태 2개가 일치했고 SQLite 무결성 검사를 통과했다. 실제 개인 DB와 실행 중인 배포 EXE는 변경하지 않았다.

다음은 4단계의 최초 선택·구독 설정 화면이다. 현재 기존 UI의 고정 출처 표시는 그 단계에서 구독 데이터와 연결한다.
